# 연구용 논문 초안 R83 — 출처 충실도와 계약 조건이 소프트웨어 변경 실험의 해석을 어떻게 바꾸는가?

**부제:** go-chi/chi `RouteHeaders`의 업스트림 수정 이력, 연구용 파생 구현, 그리고 재현 가능한 음성 결과를 구별하는 사례 연구

**Research draft / 논문 투고 전 초안 — 2026-11-23.**

**상태:** 논증·재현성·방법론 중심의 서술 초안. 외부 블라인드 E1/E2 실험은 미수행. 본문은 **새로운 ATLAS 이론 또는 사람의 판단 능력 향상**을 주장하지 않는다. 기존 Paper B v50은 REJECT/HOLD로 유지한다.

## 초록

소프트웨어 변경 실험은 원본 소스 코드, 연구자가 만든 변형, 연구자가 정의한 새 요구, 실제 업스트림 프로젝트에서 승인된 요구를 혼동할 경우 재현성이 확보되더라도 해석이 잘못될 수 있다. 본 논문은 Go HTTP 라우팅 라이브러리 go-chi/chi의 `RouteHeaders` 변경 사례를 통해 **소스 출처, 시간적 계약, 그리고 요구사항의 권한**을 구별하는 방법을 검토한다. 구체적으로 공식 v5.1.0 소스, 공식 후속 수정 커밋, 팀이 작성한 LIVE/SNAPSHOT 두 파생 구현과 그 D8 수정본을 비교한다. 팀 변형의 기존 공통 요구(D0)는 통과했으나 연구자 정의의 신규 요구(D8)는 수정 전 두 구현에서 일부 실패했고, 수정 후 두 구현에서 모두 통과했다. 후속 등록 가시성과 상태 고정이라는 서로 다른 시간적 계약은 각 구현에서 유지됐다. 한편 공식 업스트림 v5.1.0의 빈 라우터에서는 다음 핸들러 이중 호출이 재현되며, 해당 문제를 수정하고 정확히 한 번 호출을 검증하는 공식 수정 이력이 확인된다. 중요한 한계는 팀 변형의 Git blob SHA가 공식 upstream Git blob과 동일하지 않다는 것이다. 따라서 팀의 재실행 성공은 **팀 파생 구현의 재현**이지 원본 라이브러리의 전체 검증이 아니다. 설계 근거 기록의 유용성에 대한 선행 통제실험까지 고려하면, 추가적인 기록 체계의 이득은 추정할 수 없으며 실제 외부 사례에서 강한 ADR 기준선과의 공정 비교로 검증해야 한다. 본 연구는 이러한 구분을 명시한 재현성 사례와 향후 독립 평가 계획을 제시하되, ATLAS의 고유한 학술적 우월성을 주장하지 않는다.

**핵심어:** 소프트웨어 유지보수, 설계 근거, 소스 출처, 아키텍처 결정 기록, 요구사항 진화, 시간적 계약, 재현성, 음성 결과

## 1. 서론

소프트웨어의 변경이 바람직한지 판단하려면 해당 구현의 동작뿐 아니라 *어느 시점에 어떤 요구사항이 유효했는지* 알아야 한다. 동일한 코드 수정도 동적 등록의 가시성이 요구되는 환경에서는 올바르지만, 기존 핸들러가 등록 당시 상태를 유지해야 하는 환경에서는 계약 위반일 수 있다. 이러한 구분이 중요하다는 직관은 기존 요구공학·설계 근거·소프트웨어 아키텍처 연구와 상당 부분 겹친다. 본 연구에서는 이를 새로운 일반 법칙으로 제시하지 않고, **실제 소스와 연구용 변형의 경계를 혼동할 때 실험 결론이 어떻게 과장되는지**를 조사한다.

연구의 출발점은 go-chi/chi `RouteHeaders`를 바탕으로 만든 LIVE/SNAPSHOT 파생 구현이다. LIVE는 이미 생성된 핸들러가 이후의 순차 등록을 관찰하도록 하고, SNAPSHOT은 해당 핸들러의 등록 상태를 생성 시점에 고정한다. 팀은 두 구현에 공통 D0 요구 및 후속 D8 요구를 적용했다. R80 실험에서는 네 소스 상태(수정 전후 × LIVE/SNAPSHOT)를 동일한 Go 테스트로 재실행해 12개 묶음의 예상 결과와 실제 결과가 일치함을 확인했다.

그러나 후속 외부 감사에서 중요한 출처 문제가 제기됐다. 팀이 `original LIVE`라고 부르던 파일은 go-chi/chi v5.1.0의 공식 소스 바이트와 달랐다. 이후 원본 및 공식 수정 커밋을 직접 재조회하고 팀 파생 구현의 소스 해시를 대조했다. 그 결과 소스 수준에서 정확히 재현한 것이 **연구자가 만든 변형**임을 분명히 해야 한다는 결론에 도달했다.

이 논문의 목적은 특정 기록 형식의 우월성 입증이 아니다. 첫째, 소스·계약·실험 오라클의 출처가 분석 결과를 어떻게 제한하는지 보이고, 둘째, 직접 재현한 현상과 업스트림 수정 이력을 연결하고, 셋째, 강한 설계 근거 기준선을 실제로 넘어서는 편익을 판정하기 위해 필요한 실험 조건을 명시한다.

## 2. 선행연구와 연구의 위치

Conklin과 Begeman의 gIBIS는 논증 관계를 구조화하는 설계 근거 표현의 선행 사례이며, Lee와 Lai의 DRL은 결정 대안, 평가 목표, 논거 및 결정 의존 관계를 다룬다. Tang 등(2007)의 AREL은 아키텍처 설계 근거와 추적성을 연결하는 기존 방법이다. 따라서 공유 근거, 타이핑된 관계, 상황 변화에 따른 의존 결정을 표시하는 것만으로 새로운 이론이 성립하지 않는다. 이 문헌들의 기능별 대응은 기존 EvoNOMOS 문헌 원장에 기록되어 있지만, 본 R83에서 이 원전들의 전문을 다시 검증하지는 않았다.

보다 직접적인 실증 선행연구도 있다. Bratthall, Johansson, Regnell(2000)은 설계 근거 문서가 변경 영향 분석의 정확도 및 속도에 기여하는지를 17명의 참가자와 두 실시간 임베디드 시스템을 이용하여 조사했다고 보고한다. 논문 초록은 한 시스템에서 긍정적 결과가 관찰됐지만 다른 시스템에서는 결론이 명확하지 않았다고 요약한다. 이 회차에는 웹으로 제공된 초록을 확인했으나 원본 PDF 이미지의 모든 표와 통계량은 재검증하지 못했다.

Falessi, Briand, Cantone, Capilla, Kruchten(2013)은 설계 근거 기록의 정보 항목별 가치가 수행할 활동과 항목 유형에 따라 달라진다는 가설을 **75명의 석사과정 학생을 포함한 두 통제실험**으로 검토했다. 저자 소속 기관의 공식 논문 초록은 활동에 따라 일부 정보를 선택적으로 기록하는 방식이 전체 기록의 항목 수를 상당히 줄일 수 있다고 보고한다. 본 연구는 문헌 전체의 효과크기를 새로 산출하지 않았으므로, 이 결과를 새로운 인과 효과의 정량 추정에 직접 사용하지 않는다. 그럼에도 이 연구는 **과제에 맞춰 설계 근거 기록을 최소화하는 발상 자체**를 새로운 기여로 주장하기 어렵게 만든다.

따라서 앞으로의 비교는 설계 근거가 *있는가/없는가*가 아니라, 이미 풍부한 링크·상태·근거를 제공하는 **강한 ADR/AREL 기준선에 특정 시간적 계약을 명시했을 때 발생하는 추가적인 결정 효과와 추가 기록 비용**을 함께 측정해야 한다.

## 3. 사례·자료·검증 단위

### 3.1 공식 upstream과 파생 소스의 구별

| 출처 유형 | 고정 자료 | Git blob SHA | 연구상 지위 |

| 공식 upstream 후속 상태 | go-chi/chi v5.2.5 `middleware/route_headers.go` | `1c3334d35fc2b592f1ff01c03213e4779ddde338` | 후속 수정 포함 버전 |

| 연구용 SNAPSHOT 이전 상태 | EvoNOMOS `arms/snapshot/route_headers.go` | `e9ca2c3863d5aa06ef0f0b9d168ddcf184713d75` | 팀 파생본 |
| 연구용 LIVE D8 후 | EvoNOMOS `d8/live/route_headers.go` | `e481e73aa1d82497c25011b6468d7e8749c705f7` | 팀이 수정한 파생본 |
| 연구용 SNAPSHOT D8 후 | EvoNOMOS `d8/snapshot/route_headers.go` | `66e88964508cedc38740913a7c00fbf5b6e6220a` | 팀이 수정한 파생본 |

Git blob SHA는 바이트 내용 동일성을 확인하는 식별자로 사용했다. 업스트림과 연구 파생본의 해시가 모두 다르므로, 연구 파생본의 7개 파일을 정확히 복원했다는 사실이 공식 Chi의 전체 동작 재현을 의미하지는 않는다.

### 3.2 요구사항과 평가 기준

공통 D0 테스트는 빈 라우터, 헤더 우선순위, 동일 헤더의 등록 순서, 기본 폴백 및 와일드카드 라우팅을 포함한다. D8은 연구진이 추가한 우선순위 요구로, 한 헤더에서 와일드카드가 일치하더라도 다른 헤더의 정확한 일치를 먼저 선택하는 등의 사례를 포함한다. D8의 요구는 upstream 개발자가 승인한 공식 사양으로 간주하지 않는다.

시간적 계약은 별도로 정의한다. **LIVE 계약**은 핸들러 구성 이후 등록한 규칙도 기존 핸들러가 순차 호출 상황에서 관찰해야 한다는 요구다. **SNAPSHOT 계약**은 핸들러 구성 시점의 규칙 집합이 이후 등록과 관계없이 유지돼야 한다는 요구다. 두 계약은 서로 다른 응용 환경을 나타내므로 동일한 정답 행으로 결합하거나 어느 한 구현을 전역적으로 우수하다고 평가하지 않는다.

### 3.3 실행의 범위

R80의 실험은 Go 1.23.2, Linux/amd64, 격리된 네 패키지에서 수행됐으며, `-race -count=1`로 테스트했다. R80 재현 스크립트는 사용한 Go 소스 및 테스트 7개의 Git blob을 검사하고 4개 구현 × 3개 테스트 묶음을 실행한다. 이는 해당 범위의 소스 기반 재실행이지 전체 Chi 모듈의 통합 검사가 아니다. 순차적인 등록 변화 테스트가 통과했다는 사실로 동시성 상황에서의 맵 변형 안전성을 증명할 수도 없다.

## 4. 결과

### 4.1 연구팀 파생 소스의 D0/D8 적합성

| 팀 파생 구현 | D0 | 신규 D8 | 사후 등록의 순차 관측 |
| --- | --- | --- | --- |
| 수정 전 LIVE | PASS | FAIL (5개 하위 사례 중 2개) | 새 등록 반영 |
| 수정 전 SNAPSHOT | PASS | FAIL (동일 2개 사례) | 이전 상태 유지 |
| D8 수정 LIVE | PASS | PASS | 새 등록 반영 |
| D8 수정 SNAPSHOT | PASS | PASS | 이전 상태 유지 |

D8의 실패 사례는 `later-exact-over-earlier-wildcard`와 `route-any-exact-pattern-matches`였다. 수정 후 두 파생 구현은 동일한 D8 테스트를 통과했다. 두 구현의 시간적 계약도 유지됐다. 이 자료는 **하나의 새 요구에 대해 두 상이한 시간적 설계가 모두 수정 가능했음**을 보여주지만, 수정 시간·후속 유지보수 비용·리뷰 정확도에 관한 승자를 결정하지 못한다.

### 4.2 실제 upstream의 빈 라우터 동작과 후속 수정

공식 v5.1.0 소스의 빈 라우터 분기에서는 `next.ServeHTTP` 호출 이후 즉시 반환하지 않았다. 같은 요청이 다른 라우팅 경로를 거쳐 다음 핸들러에 다시 도달할 수 있었고, 해당 입력에 연구팀의 정확히 한 번 호출 테스트를 적용한 격리 재실행에서 실제 두 번 호출되는 결과를 관찰했다.

이 현상은 [공식 수정 커밋 `05f1ef7...`](https://github.com/go-chi/chi/commit/05f1ef7bb50b8a8cb33a9dd3ba1c5b94bff0f723)과 독립적으로 대조할 수 있다. 업스트림 개발자는 빈 라우터에서 두 번 호출되는 문제를 수정하기 위해 `return`을 추가하고 회귀 테스트를 작성했다. 공식 v5.2.5 소스에서도 해당 반환문과 테스트가 확인된다. 따라서 이 부분은 사후의 외부 개발 이력으로 확인되는 실제 결함 사례다. 그러나 **이것이 EvoNOMOS 연구로 처음 발견됐거나 해당 수정이 연구 성과였다는 주장은 하지 않는다.**

반대로 D8에서 정의한 정확한 패턴 우선순위는 연구팀의 별도 계약이다. 업스트림이 그 요구를 충족하지 않는 것은 직접적으로 원래 프로젝트의 버그를 의미하지 않는다.

### 4.3 계산 비용에 관한 탐색적 관측

R81은 D8 수정본 LIVE/SNAPSHOT을 대상으로 요청마다 경로를 탐색하는 비용과 핸들러 생성 시 규칙을 복사하는 비용을 나눠 측정했다. 연구 기록은 요청 반복이 적을 때 LIVE가, 핸들러당 요청 재사용이 충분히 많을 때 SNAPSHOT이 빠른 양상을 보고한다. 또한 생성과 조회를 합친 실험은 사전 지정한 본 시험 이후 설계한 **사후 탐색 실험**이었다. 이러한 마이크로벤치마크는 팀 파생 코드의 구체적인 처리 비용을 설명하는 데 도움이 되지만, Go 런타임·하드웨어·라우트 수·요청 분포·GC 조건을 바꿔도 일정한 비용 교차점을 보장하지 않는다. R81 결과를 사람의 유지보수 시간이나 원래 Chi의 서비스 성능으로 승격하지 않는다.

## 5. 방법론적 분석

### 5.1 재현성의 세 층

본 사례에서 재현성은 다음의 서로 다른 층을 갖는다. **(i) 바이트 충실도:** 연구팀 파생 파일을 정확히 복원했는가. **(ii) 실행 충실도:** 고정된 소스와 테스트가 일관된 결과를 내는가. **(iii) 대상 충실도:** 그 결과를 연구자가 주장한 실제 외부 시스템·조직·사용자 모집단에 일반화할 수 있는가. R80은 앞의 두 층에서 비교적 강한 증거를 제공하지만 세 번째 층을 만족하지 않는다.

비슷하게 테스트의 실패는 `실제 구현 ≠ 적용한 요구`를 보여줄 뿐이다. 그 요구가 실제 제품의 승인된 계약인지 별도 확인해야 하고, 요구의 내용이 실험자가 결과에 따라 수정됐는지도 기록해야 한다. 원래 구현과 다른 시간적 계약을 지닌 구현은 특정 계약에서 실패해도 일반적인 의미에서 열등하지 않을 수 있다.

### 5.2 기존 ADR과의 공정 비교

두 방법에 다른 정보를 제공한 뒤 정확도만 비교하면, 나타난 차이가 표기 체계 때문인지 정보량 때문인지 식별할 수 없다. 향후 실험은 **강한 typed ADR + 소스 링크 + 변경 상태 + 사용 가능한 모든 이력**을 기본 기준선으로 두고, 추가 시간적 계약 필드의 인과적 편익만 검증해야 한다. ATLAS 전용 특수 라벨이 정답 기준이 되지 않도록 gold는 소스·계약과 실제 관측을 바탕으로 독립 판정자가 구성해야 한다.

## 6. 위협 및 한계

**내적 타당도:** D8의 새 요구와 테스트 오라클은 같은 연구진이 작성했다. 순서도 초기 결과 뒤에 설계됐으므로 독립 사전등록 실험으로 분류하지 않는다. Git blob 일치는 표본을 바꾸지 않았음을 보장하는 한 가지 검증이지만, 오라클이 공정하다는 증명은 아니다.

**구성 타당도:** 정확성·계산 비용·기록 비용·사람의 판단 속도는 서로 다른 결과 변수다. 한 변수에서 얻은 개선을 다른 변수로 전이하지 않는다. 모형별 LIRA 우선도 점수는 주관적 자원 배분 판단이지 검정된 효과 크기나 확률이 아니다.

**외적 타당도:** 연구 파생 라우터는 특정 한 사례이고, R80과 R81은 완전한 upstream Chi 애플리케이션이나 다수 조직의 유지보수 실험이 아니다. Go 맵 순회, 소스 복사 시점, 요청 반복 횟수에 대한 기계적 차이가 다른 언어·런타임·아키텍처에도 그대로 성립한다고 일반화하지 않는다.

**문헌 검토 범위:** Falessi 외(2013)의 대학 공식 초록은 직접 확인했으나 원문 통계표 전체를 재분석하지 않았다. Bratthall 외(2000)는 웹으로 제공된 논문 초록을 확인했으며 이미지 페이지 대조는 미완료다. DRL·AREL의 세부 기능 대응 역시 전체 최신 문헌 검증을 이 원고에서 완료했다고 주장하지 않는다.

**독립적 사람 평가 부재:** 외부 개발자에 의한 블라인드 정답 판정과 리뷰 시간 비교는 수행되지 않았다. 이를 수행하지 않은 상태에서 새로운 기록 형식의 유익함을 주장할 수 없다.

## 7. 향후 실험: 기존 방법에 계약 정보를 추가하는 최소 개입

후속 E1의 표본은 연구진이 아직 결과를 읽지 않은 **외부 프로젝트의 실제 변경 에피소드**로 구성해야 한다. 독립적인 사례 선정자가 시점과 커밋 해시를 고정하고, 둘 이상의 판정자가 소스·이슈·문서에서 실제 적용 계약과 관측 가능 결과를 판정한다. 실험 조건은 (A) 강한 typed ADR 전체 정보와 (B) 동일 ADR 정보에 특정 시점의 계약 표시를 명시한 형태다. 중요한 것은 두 조건의 사실 정보량을 최대한 일치시키고, 필드 존재 여부가 정보 누락을 의미하지 않도록 해야 한다는 것이다.

주요 결과는 기존 유효 계약을 정확히 회수하는 비율, 잘못된 철회 또는 유지 비율, 정당한 판정 유보율이다. 선택적 항목 추가의 실제 기록 시간과 이력 회수 시간도 함께 측정한다. 참가자와 사례의 군집 종속성을 반영하고, 표본 수·배정·중단 규칙은 사례를 열람하기 전에 고정한다. 이미 본 [go-chi/chi #1045](https://github.com/go-chi/chi/commit/05f1ef7bb50b8a8cb33a9dd3ba1c5b94bff0f723)는 훈련·개발 사례로만 사용하고 held-out 표본에 포함하지 않는다.

해당 실험에서 강한 ADR이 동등하거나 우월하고, 계약 필드의 작성 부담이 유의미하게 늘어난다면 별도 형식 연구를 중단하고 기존 ADR의 선택적 보조 항목 수준으로 환원한다. 반대로 추가 항목이 반복 가능한 독립적 편익을 보인다면 해당 차이에 한정된 작은 결과로 보고한다. 이 단계의 기대는 **비용·정확도를 실증하겠다는 계획**이지 유리한 결과가 나올 것이라는 주장도 아니다.

## 8. 결론

go-chi/chi 사례에서 공식 태그 원본, 공식 수정 커밋, 연구 파생 소스 및 연구자 정의 요구사항을 구분하자, 이전에 동등하게 다뤄지던 테스트 결과들의 해석 범위가 달라졌다. R80은 팀 파생 Go 구현의 고정된 요구 충족 여부를 재현했고, 공식 업스트림 이력은 특정 이중 호출 결함에 관한 외부 수정 증거를 제공했다. 반면 독립 ATLAS의 우월성이나 사람의 검토 효율은 입증되지 않았다. 기존 설계 근거의 선택적 문서화와 비용·효과에 대한 선행실증을 고려하면, 새로운 이론을 확장하기보다 **실제 외부 사례에서 강한 기존 방식과 동등 조건으로 작은 추가 정보의 가치를 측정하는 연구**가 우선이다.

본 초안은 새로운 시스템을 주장하는 논문이 아니라 **기존 실험의 출처 교정, 재현 가능한 제한적 관측, 음성 결과, 그리고 후속 실증 설계**를 다루는 연구 보고다. 외부 평가 이전에 완결된 실증 논문으로 간주하지 않는다.
