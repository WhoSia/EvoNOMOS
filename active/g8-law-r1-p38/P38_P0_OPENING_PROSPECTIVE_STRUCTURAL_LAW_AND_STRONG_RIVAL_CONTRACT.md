## 0. Inherited original question and boundaries

EvoNOMOS was founded to discover falsifiable, *conditional* structural design laws of actual software evolution, including domains where SOLID-style recommendations succeed, fail, or reverse. Methods—GitHub Actions, HWPX/docs, code graphs, metrics, CI success, predictive AUC, prompt tools—are infrastructure rather than the explanandum. Do not demote this objective to generic governance or code-review automation.

**Predecessor:** [P37-MATH-L](../g8-law-r1-p37/P37_MATH_L_RESOURCE_BOUNDED_PREDICTIVE_SUFFICIENCY_AND_P38_PROPOSAL.md) found a three-query certificate complexity within the pre-existing source-API-tethered researcher-built E4 graph, and a separate synthetic discovered-handle graph indistinguishability bound. Both are **classical**. [P37-MATH-K](../g8-law-r1-p37/P37_MATH_K_CLASSICAL_EXPRESSIVITY_BARRIER_AND_OWNER_OBLIGATION_IDENTIFIABILITY_COURT.md) showed exact full-information classical repair reachability predicts the same Boolean outcomes as any exact correctly specified repair model. Prior source results E1–E4 are **CALIBRATION / IN-SAMPLE**, never an undisclosed P38 holdout.

**The scientific P38 question:** Under authentic historical source ownership, allowed cross-owner edit actions, invariants and upcoming maintenance requests, can a small source-grounded **repair certificate and design-choice predictor** deliver a reproducible prospective advantage over the strongest *implementable* prior-art competitors given strictly **identical evidence and measured total query/compute budgets**? Can it predict a CONDITIONAL DESIGN CHOICE REVERSAL rather than merely classify a known compatibility check?

The strongest exact classical semantics remains undefeated and is explicitly allowed as a perfect-oracle upper bound. The challenge is evidence-, time- and resource-bounded *prediction*, not logical expressivity over fully known models.

## 1. Prospective case unit, clocks, and evidence provenance

For each case i, immutable source ecosystem R, repository commit SHA s_i and calendar cutoff t_i must be frozen **before** the future target outcome is inspected. A case is (real original dependency across independently maintained modules; historical owner/maintainer evidence; an actual change request d_i after or at the registered prediction window; source-derived allowed edit grammar Γ_i; checkpoint invariant I_i; target y_i; prediction sign, confidence/certificate; budget receipts).

**Two possible valid designs, not to be conflated:**
1. *Truly prospective*: register a future demand and predictions while the relevant downstream repair outcome is not yet available; inspect its future outcome only after the seal. This may have slow follow-up. The request must be evident at/within the prediction cut. Do not claim it is prospective merely because the source repo is live.
2. *Temporal replay on historical releases*: freeze all evidence and model decisions to historical cutoff t_i, choose historical later events as held-out outcomes, and enforce output-blind handling through isolated evaluation. Call this **historical out-of-time retrospective**, never a true prospective result. Merely agreeing to withhold known future labels does not erase possible design-time contamination from modern knowledge.

**Forbidden label leakage:** target PR merge status, post-cut commit diff, post-cut tests or docs, after-the-fact issue discussion, analyst-curated answer summaries, current upstream HEAD in place of t_i, or predictions adjusted after reading outcome. Public access is not the same as admissibility.

**Authentic rights:** GitHub CODEOWNERS, reviewers, signed maintainer communication, explicit release obligations, code-defined capability requirements and actual edit permissions each have different evidence weight. Neither file commit history nor an author-by-file heuristic automatically proves the legal authority to edit, veto, or deploy. Where owner or obligation cannot be substantiated, flag UNKNOWN and reduce or refuse case eligibility; never fabricate a ground truth partition.

**Unbounded semantics vs actual outcome:** mathematical May under a restricted Γ/I is NOT identical to a maintainer deciding to complete a patch. Register separate targets: (A) certified finite-grammar reachability, (B) natural observed patch adoption/partial completion, (C) preserved invariants in reproducible native tests. State causal/selection and effort confounds explicitly for B.

## 2. Shared evidence and resource ledger

For each pair of competitors fix **exact same** public source snapshot, source-history window, issue/requirements text and known governance/permission facts. Both get identical data types and an identical discovery oracle. H must not be handed precomputed permission cuts or a favorable source graph unless B can build/use that feature from the same evidence, with feature construction **charged** to H's account. Rival may include preprocessing, caching, adaptive queries, graph propagation, co-change models, static/dynamic program analysis, assume–guarantee reasoning and Bayesian/decision-tree search when available.

Declare separately:
- B_I: per-case information calls or annotated evidence bytes/lines available, with controls on metadata and indirect leakage. If information can be read in one bulk call, count its full bytes/units—not artificial one-bit constraints borrowed from P37-MATH-L.
- B_C: CPU time, memory peak, candidate/state expansions, source-line parse count, and **preprocessing + feature construction** costs with hardware/runtime pinned. Claim equal-resource comparison only for enforced units, not a single scalar runtime estimate.
- B_H: historical outcome/tuning budget, identical and cutoff-respecting for both. Distinguish frozen training and validation from future locked cases.
- B_A: expert annotation/label construction hours per system. Researcher-derived source graphs must be costed; hidden hand-labeled owner graphs cannot be freely given to H.

If an exact competitor uses the same evidence and compute to derive the same certificate/decision, record **NO SEPARATION**, not an allegedly weak baseline defeat. Use an unrestricted classical verifier on small feasible scopes as ceiling/control, not a baseline expected to work on unlimited Go source.
