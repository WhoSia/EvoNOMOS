## Executive scientific assessment

The best **new paper direction** in the P35–P38 arc is NOT "a novel source-repair equivalence theorem" or "we showed SOLID failed". The genuinely underexplored, falsifiable *joint empirical prediction* is:

> Given actual original-source edit choices and reviewer-owned constraints, when does a proposed implementation reuse or architectural simplification preserve future repair options and semantic contracts, and when is its real-world adoption blocked by source API rights, implementation behavior, or maintainer decision? Can a source-evidence- and compute-budget-matched model predict future decisions better than a strong classical model?

Each clause is individually explainable by serious existing work. The paper's potential contribution would have to be **prospective, replicated and operationally distinct predictive value**, not a claim of having invented behavioral refinement or maintainer approval.

## Leading candidate (priority A)

**Working title:** *When Reuse Is Not a Repair: Contract-Indexed Source Evolution and Cross-Maintainer Patch-Option Survival.*

**Research questions** (split targets and hypotheses before evaluation):

- **RQ1 contract preservation.** On a prospective repository/source cutoff, do predictions of future parity/regression under future requests improve from a typed source-edit/owner repair representation over an equally informed resource-limited implementation of behavioral refinement/assume–guarantee, dependency-history, neural change-effects and cost-aware query selection? Outcome = independent original source behavior under fixed oracle; missing execution = ABSTAIN, not automatic failure.
- **RQ2 source option preservation.** Does a particular source architecture have more **independently source-verified alternative future repair paths** within a prospectively delimited edit grammar, after identical demand sets, API/ABI constraints and real owner permissions? A witness path proves MAY, not universal exhaustion; a lower bound on feasible options requires an audited grammar/closed search, and sampling cannot silently become exact counts.
- **RQ3 maintainer adoption.** Can the same model separately predict future PR accept/reject/deferral, controlling for review policy, burden, owner turnover, source-level semantic fit and censoring? Adoption is **not** an interchangeable label for code feasibility or mathematical reachability. No unearned causal attribution from observational review data.
- **RQ4 conditional reversal.** Under what prespecified demand/legacy-obligation/maintainer resource moderators does a ranking of two actually feasible **competing** architectures or repair policies reverse at fixed functional requirements? If Q changes between arms, label it contract-indexed feasibility, not same-Q cost inversion. Preselect subgroup contrast and independent source holdout.

One eligible prospective unit:
(original upstream SHA, actual imported upstream tag SHA, downstream SHA, cutoff timestamp, actual maintainer/reviewer evidence and uncertainty, verbatim pre-outcome request, semantic contract Q, allowed source-edit grammar, invariant checkpoints, original API and ABI constraints, implementation options A/B and source provenance, shared label-free information and compute budget, H/B implementations and frozen digests, different preregistered H/B predictions, label oracle/horizon, missingness/censoring and receipts).

Explicit label columns:
1. **S_API:** source API accessibility / whether a named path is directly callable under restricted grammar (not semantic correctness);
2. **S_Q:** prospective old/new contract preservation on independent inputs and histories (PASS/FAIL/ABSTAIN);
3. **S_MAY:** restricted-grammar source repair path witness or sound impossibility certificate (YES/NO/UNKNOWN);
4. **S_REVIEW:** reviewer decision (accepted/rejected/withdrawn/pending/no reviewer), with dates and competing explanations;
5. **S_COST:** preprocessing + compilation/test + human annotation + memory/time/resource vector rather than a single unreported scalar.

Never coerce pending or documentation-only closure into "repair succeeded", never use PR closure alone as semantic NO.

## Other paper candidates with negative filters

**Candidate B — *Owner-Obligation Information Bounds for Source Repair*.** P37 MATH-I–L show demand quotient, owner authority and information-query lower bounds under a finite restriction. These are **classical** kernel factorization, μ-calculus reachability, decision-tree complexity and amortization. Without a genuinely new complexity separation, expressive theorem or nontrivial structural invariant, this is a mathematically clear **methods appendix**, not a claimable new theoretical paper.

**Candidate C — *When Issue Closure Is Not a Source Repair: The Semantics of Maintainer Decisions*.** Observational mining of documentation-only closures versus behavior changes and rejected source patches across independent repositories. A worthwhile empirical question, but Papotti et al. have already studied code-review acceptance and technical patch quality, while issue-label noise and selection/censoring are major risks. Requires reproducible independent multi-repo cohort, nontrivial baseline, label adjudication and actual uncertainty; one Fiber/fasthttp sequence cannot establish empirical prevalence.

**Recommendation:** A as primary manuscript track, C as related empirical mechanism or follow-on, B as technical appendix pending new mathematics. This is an **editorial recommendation**, not proof of publication suitability.
