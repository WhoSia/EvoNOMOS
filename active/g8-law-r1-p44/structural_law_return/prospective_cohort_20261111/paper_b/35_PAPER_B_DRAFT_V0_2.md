# Paper B, v0.2 — From Strategic Closure to Code Labels

Historical argument draft · 2026-11-17 KST

## Abstract

When can a finding of an open–closed principle (OCP) violation support a maintenance decision? We compare the evidence required by early accounts of extensibility with the evidence supplied to one automated classification study. Meyer places an extension alongside a stable description available to clients. Martin makes the choice of changes against which a module should be closed explicit. In the later study, the archived prompts ask a model to classify code. They supply no separate item-specific change request or protected client contract in the inspected templates. Related instruments already use expert assessments, concrete extension scenarios and executable structural checks, making it possible to locate the narrower issue of how a classification supports a particular decision. A fixed-patch reconstruction demonstrates that the same code can be acceptable or unacceptable as two premises vary independently. The decision can sometimes be settled with one premise and sometimes needs further evidence. We propose that review instruments expose the extension, the client obligations and the affected boundary when their judgments are used to justify an edit.

## 1. What is the program supposed to stay closed against?

In 1988 Bertrand Meyer asked how a library program could accommodate technical reports. One design puts the distinctions among publication kinds in an existing module. Adding a kind that needs its own behavior then requires another edit to that module. The point of describing a module as closed was that other modules could use it on the basis of a stable description. The example puts two concrete concerns into the same engineering decision: the work needed to support a new kind and the continuity that downstream clients can expect. [Meyer, first edition, pp. 22–25](./13_MEYER_FIRST_EDITION_PASSAGE_RECOVERY.md).

Robert Martin explicitly paraphrased Meyer in 1996 and gave source modification a prominent place in the formulation. His drawing example then sets limits on what that formulation can tell a designer. A routine written against a shape abstraction can draw a new kind of shape without changing the routine. When the requirement becomes drawing every circle before any square, the existing routine lacks the ordering policy. Martin asks designers to select the changes against which to seek closure, with that selection informed by their users and a judgment about likely requirements. The same routine therefore supports two different assessments once the question about its future changes. [Martin 1996, pp. 1, 6–9](https://www.cs.utexas.edu/~downing/papers/OCP-1996.pdf).

These examples make an OCP assessment conditional in a way that matters to people working on the program. A designer needs to know what must be added and whose existing work has to remain usable. Automated review introduces a further possibility: that an assessment made against the conventions of a classification task will be reused to support a decision about an actual edit. We ask what information survives that move.

## 2. What three kinds of measurement make explicit

Bräuer and colleagues put forward measurable design practices and asked focus groups how much of each principle those practices captured. The three groups considering OCP assigned between 9 and 32 points on a 100-point scale to features of the principle still left uncovered. The participants made these assessments after considering the proposed practices and any suggestions they had made. The results record how complete practitioners considered an operational definition to be. [Bräuer et al. 2018, §§4.2–4.3 and Table 6](https://doi.org/10.1016/j.jss.2018.03.002).

Cabral and colleagues supplied participants with versions of industrial machine-learning code and presented a scenario in which it had to accommodate more regression models. Participants judged how easily the supplied code could be understood and extended and whether extending it would require changing existing code. The pooled responses favored the SOLID refactoring for those questions. One treatment changed all five principles together, and the measured outcomes were questionnaire responses to supplied code. This is a different way to give an OCP assessment a concrete extension. [Cabral et al. 2024, §§3.4, 4–5 and Table 6](https://doi.org/10.1145/3644815.3644957).

In *Needle in the Repo*, Zhu and colleagues give agents explicit repository changes and use hidden functional tests and structural oracles. In a numeric addition case, the existing call sites must remain untouched while support expands to further types. The oracle checks for a reusable core and restricts per-type overloads. In an inline-filter case, the visible request specifies the feature and asks to preserve behavior, while the reuse criterion is implemented in the evaluator. Across the suite, 64 of 483 configuration–case outcomes passed the functional tests and failed the structural oracle. The example makes two distinct questions inspectable: what an agent sees when making a choice, and what an evaluator uses when scoring it. The oracle is tied to the authors' engineering specification. Its score establishes conformance to that specification. [Zhu et al. 2026, §§2–3, 5.3, 6.2](https://doi.org/10.48550/arXiv.2603.27745).

## 3. What a code label can establish

*Are We SOLID Yet?* evaluates prompt-based detection against reference labels. In the archived OCP subset we inspected 48 code pairs and 768 saved prompts. Removing the single copy of the submitted code from each prompt leaves 24 distinct templates. None contains a separately stated item-specific change demand or protected client contract. Several templates provide general design cues. An individual snippet can still carry clues, and a complete provider request could contain further material. Our analysis concerns the saved prompts. [Pehlivan et al. 2025](https://arxiv.org/abs/2509.03093) · [Archive audit and inventory](./18_ARE_WE_SOLID_OCP_ARCHIVE_AUDIT.md).

One pair illustrates why the distinction matters. The output places area calculation behind a shape method and omits several getters declared in the input, including Rectangle.get_width. Under a contract limited to the displayed area calculation, a judgment could focus on extension through a new shape. A caller that used the omitted width getter would raise a separate compatibility question. The archive records the source declarations and labels. Whether such a caller existed or was entitled to use that method remains open.

The benchmark's labels permit comparison of model classification against reference judgments. The merge decision for a particular real change additionally needs some account of the new work, the client obligations and the permitted repair surface. An evaluator can supply those premises explicitly, or they can be recovered from sources such as tests and client documentation. For the second route, the report should make the provenance of those premises inspectable.

## 4. A reproducible decision under two specifications

We implemented a small version of the library scenario. Our candidate adds a report provider without changing either existing source file. It renders a report, capitalizes the book prefix and leaves errata unsupported. We hold the same candidate and edit boundary fixed, then vary whether errata must also be supported and whether the existing book prefix is protected. Under the report-only demand and the narrower client contract the patch satisfies both obligations. Adding either obligation defeats it for a different reason. All four specifications are jointly feasible in the sense that one other additive provider satisfies each of them. The observed changes in acceptance are attributable to the change in which criteria the fixed patch has to meet. [Executable comparison](./31_OCP_FIXED_PATCH_DEMAND_AND_CONTRACT.md).

We also replay the decision with some requirements withheld. If the current evidence permits several task specifications, agreement across them warrants a conditional acceptance or rejection. Disagreement identifies a fact that still needs to be settled. Requiring errata, for example, warrants rejection in this witness regardless of whether the book prefix is protected. Giving the report-only requirement while withholding the book obligation leaves acceptance open. The replay uses a finite list of author-specified alternatives. It leaves open how reliable reviewers or models are at recovering the right alternatives from a repository. [Partial-disclosure replay](./34_MAINTENANCE_JUDGMENT_UNDER_PARTIAL_DISCLOSURE.md).

## 5. Discussion

A design principle used in a review tool can direct attention to a plausible trouble spot. For a report that also supports changing a program, we propose stating the change at issue, the behavior existing clients can rely on, and the implementation boundary the edit is allowed to cross. These commitments let a maintainer ask which observation would settle a dispute, or which stakeholder can settle it. Where several specifications remain plausible, the report can show which decisions survive that uncertainty.

The historical comparison traces a documented Meyer–Martin citation alongside separately documented practices of measurement and classification. Later examples are comparisons in how extensibility judgments are made, with any claims of direct influence left to further evidence. The implementation is a constructed witness. Broader claims about how prevalent these omissions are, how different reviewers respond to them, or whether collecting the missing context reduces maintenance costs require independent cases and measurements. One next evaluation would vary which premises a reviewer or model can inspect on the same candidate edit, and score its decisions against the known specifications as well as its ability to identify which evidence is missing.
