## A concrete implementation distinguishes compilation from recompilation

Richard L. Schwartz's [JPL report 77-4](https://ntrs.nasa.gov/api/citations/19770015903/downloads/19770015903.pdf), dated 1977 on the formal title page, describes a DEC-10 implementation in §3.3. The class or procedure is compiled first and emits an attribute file used to check later dependent compilation. His small program has two procedures referring to an external `order` class and a main program using both; dependency edges determine a serial bottom-up order (printed pp. 17–20).

Schwartz argues that, in principle, a purely internal edit should leave the attribute file untouched. He contrasts that with the handbook's qualified claim that recompilation of other modules is unnecessary in most cases (p. 20). The explanation he proposes for that limitation is conjectural. His own design target in §4 is that a module rebuild should force no other rebuild unless the actual interface changes, together with complete type checking (pp. 20–21). That is a design goal of his proposal, not a measurement of the proposal or a guarantee made by the existing DEC-10 implementation. In §5.2 (pp. 24–25), `ASSUME` declares the expected interface and `RELEASE` bounds names available to the separately compiled unit. The proposal can thus make a compiler's view of dependency more precise without establishing the behavior of future replacements.

A historical paper can now separate three concrete questions: can the toolchain incorporate a declaration compiled elsewhere, does a change force existing dependents to be rebuilt, and do existing clients still observe the behavior they rely on? The 1967 and 1977 documents directly support the first two distinctions. The last question is an interpretive bridge into the Meyer/Martin comparison and the modern executable example.
